Parte 1: Conceptos Fundamentales

1. Protocolos de Aplicación y Encapsulación

¿Qué es un Protocolo de Aplicación?

Un Protocolo de Aplicación es un conjunto estructurado de reglas que determinan cómo las aplicaciones en diferentes computadores se comunican entre sí. Define:

  • El tipo de mensajes que se intercambian (ej. Peticiones/Requests y Respuestas/Responses).
  • La sintaxis de esos mensajes (qué campos tienen y cómo están organizados).
  • La semántica (el significado de la información en esos campos).
  • Las reglas para saber cuándo y cómo enviar los mensajes.

El Flujo de Bits en la Encapsulación

Cuando envías un mensaje (ej. un email), este no viaja mágicamente por el cable. Tiene que descender por las capas de red, sufriendo un proceso llamado encapsulación, donde cada capa envuelve al mensaje con un encabezado (Header) nuevo.

Data Link Header Añade dir. MAC (Trama)
IP Header Añade dir. IP (Paquete)
Transport Header Añade Puerto TCP/UDP (Segmento)
Application Data El mensaje original (HTTP, SMTP, etc.)

Ojo con los nombres: Aplicación + header de transporte = segmento (TCP) o datagrama (UDP); + header IP = paquete; + header (y trailer FCS) de enlace = trama. Las diapositivas lo describen como "muñecas rusas": cada capa envuelve completa a la anterior.

Del mensaje a los bits: Una vez que el mensaje original tiene todos estos encabezados (MAC + IP + Puerto + Datos), la tarjeta de red (Capa Física) toma esta trama de ceros y unos y la convierte en señales eléctricas, pulsos de luz o radiofrecuencias (Wi-Fi) para enviarlo por el medio físico. Al llegar al destino, ocurre el proceso inverso (Desencapsulación).

2. Puertos, Sockets y la IANA

¿Qué es la IANA?

La IANA (Internet Assigned Numbers Authority) es la entidad global encargada de coordinar los identificadores únicos en Internet, como las direcciones IP y, muy importante, los números de puerto (enteros de 0 a 65535). Los clasifica así:

  • 0 - 1023: Bien conocidos (well-known). Servicios del sistema operativo o de gestión de Internet. Ej: 22, 25, 80, 443.
  • 1024 - 49151: Registrados. Protocolos aceptados y normalizados por el IETF.
  • 49152 - 65535: Dinámicos / efímeros. Los usan las conexiones TCP para liberar el puerto principal; al cerrarse la conexión, el puerto queda disponible de nuevo.

Dato aparte: que en Linux haga falta ser root para abrir un puerto < 1024 es una convención de Unix, no una regla de la IANA.

¿Cómo se asigna un puerto? Alguien propone un protocolo al IETF → el IETF lo acepta y normaliza → la IANA le asigna uno o más puertos → el IETF publica el RFC (versión 1, revisión de comentarios, versión definitiva).

Socket vs Puerto

Es común confundirlos, pero son cosas distintas:

  • El Puerto: Es solo un identificador lógico numérico (como el número de un departamento en un edificio). Sirve para que el Sistema Operativo sepa a qué programa entregar el mensaje.
  • El Socket: Es la interfaz de software (API del sistema operativo) que un programa usa para intercambiar datos por la red. Es un objeto lógico, no físico. Un socket local queda asociado a [Dirección IP + Puerto + Protocolo (TCP/UDP)].
  • La conexión TCP se identifica por la tupla completa [IP origen, Puerto origen, IP destino, Puerto destino, Protocolo]. Por eso un servidor puede atender miles de clientes a la vez en el mismo puerto 80: cada conexión difiere en la IP o el puerto del cliente.

Dos tipos de socket

  • Con conexión (TCP, SOCK_STREAM): canal confiable con control de pérdidas, orden y flujo. Requiere establecer la conexión antes de enviar.
  • Sin conexión (UDP, SOCK_DGRAM): se envían datagramas sueltos, sin ningún control. Más liviano y rápido.

Servidores con IP privada: NAT y Port Forwarding

Si el servidor está detrás de un router con NAT (IP privada), se configura port forwarding: el NAT recibe la petición en su IP pública y un puerto dado, y la reenvía a la IP privada correspondiente. La tabla nombre↔puerto vive en el SO, en Linux en /etc/services (ej. ssh 22/tcp).

3. Conexiones Remotas: TELNET vs SSH

En la capa de aplicación existen protocolos específicos para administrar computadores y servidores de forma remota a través de una terminal o consola de comandos.

TELNET (Puerto 23)

Uno de los protocolos más antiguos de Internet (RFC-854). Es Cliente-Servidor sobre TCP y crea una terminal virtual: lo que tipeas se envía al servidor, que lo interpreta con un shell (bash) y te devuelve la respuesta.

Truco útil: telnet servidor [puerto] también sirve para hablar "a mano" con otros servicios de texto, como HTTP (80) o SMTP (25).

⚠️ El Problema: TELNET envía ABSOLUTAMENTE TODO en texto plano (sin cifrar), incluida tu contraseña. Un atacante puede leerla haciendo sniffing o, peor, ponerse en medio de la comunicación (Man in the Middle) y leer o modificar lo que pasa. Hoy se considera obsoleto e inseguro.

SSH (Puerto 22)

SSH (Secure Shell) nació como el reemplazo seguro de TELNET. Cumple exactamente la misma función de acceso a consola remota, pero con seguridad integrada.

✅ La Solución: SSH (sobre TCP, RFC-4253) cifra toda la comunicación, desde la autenticación hasta los comandos que ejecutas. Si un atacante intercepta el tráfico, solo verá caracteres incomprensibles. Además permite crear túneles cifrados.

SSH usa dos algoritmos:

  • Asimétrico (RSA/DSA): para la identificación (handshake y autenticación del usuario).
  • Simétrico (AES, 3DES, Blowfish): para el intercambio de datos, porque es mucho más rápido.

4. La Web, HTTP y Certificados X509

La Web nace a principios de los 90 en el CERN y se apoya en tres piezas: HTTP (puerto 80), HTTPS (puerto 443) y el lenguaje HTML. HTTP es Cliente-Servidor y stateless (sin estado): el servidor no recuerda peticiones pasadas del mismo cliente (por eso se inventaron las cookies).

¿Qué hace el navegador?

  1. Resuelve el nombre del servidor con el DNS.
  2. Se conecta al servidor usando la dirección IP (TCP, puerto 80/443).
  3. Pide y recupera la primera página (index.html, index.php...).
  4. Por cada objeto enlazado en la página (imágenes, CSS, scripts), se conecta al mismo servidor o a otro para descargarlo.

Páginas estáticas vs dinámicas

  • Estáticas: su contenido no cambia en el tiempo; el servidor entrega el mismo archivo a todos.
  • Dinámicas: el contenido no está fijo; se genera en el servidor en el momento (ej. PHP consultando una base de datos) y evoluciona con el tiempo.

HTTPS (Puerto 443) y Certificados X509

Igual que Telnet, HTTP envía todo en texto plano: contraseñas, formularios con datos privados... HTTPS es HTTP sobre SSL/TLS: cifra la conexión. Igual que SSH, usa un algoritmo asimétrico para autenticar e intercambiar una clave, y luego uno simétrico para los datos. Pero, ¿cómo sabes que el servidor es realmente tu banco y no un impostor? Para eso está el Certificado X509.

El servidor envía su certificado, firmado por una CA (Autoridad de Certificación) confiable. El navegador verifica la firma de la CA; si no es válida, el certificado expiró o el dominio no coincide, el navegador muestra una alerta de seguridad ("Your connection is not private") y el usuario tendría que aceptar una excepción para seguir.

5. Correo Electrónico: SMTP, MX y MIME

El email fue la primera killer application de Internet. SMTP / ESMTP (Simple Mail Transfer Protocol, puerto 25; 465 con SSL/TLS; RFC-821, RFC-5321) permite enviar correo entre usuarios de redes distintas sin saber dónde está físicamente el destinatario: basta su dirección de correo.

Los 3 elementos básicos

  • User Agent (UA): el programa del usuario para leer/escribir correo (Thunderbird, Outlook, Webmail, mutt).
  • Mail Transfer Agent (MTA): el servidor de correo (sendmail, postfix). Transfiere los mails, maneja las colas de espera y las casillas locales.
  • El protocolo: SMTP / ESMTP.

SMTP es para enviar. Para leer el correo desde el servidor se usan IMAP o POP3.

¿A qué servidor se envía? El registro MX

Para alguien@gmail.com, el MTA consulta en el DNS los registros MX del dominio gmail.com:

gmail.com. MX  5 gmail-smtp-in.l.google.com.
gmail.com. MX 10 alt1.gmail-smtp-in.l.google.com.
gmail.com. MX 20 alt2.gmail-smtp-in.l.google.com.

Menor valor = mayor prioridad. Se prueba primero el 5, si falla el 10, y así.

Algoritmo del MTA

  1. Intenta entregar al MX de mayor prioridad (menor número). Si no funciona, intenta con el siguiente.
  2. Si ninguno responde, deja el mail en su cola local.
  3. Cada intervalo Δt procesa la cola y reintenta cada mail.
  4. Si tras N intentos no logra enviarlo, abandona y le manda un mensaje de error al remitente (From: Mailer-Daemon).

Diálogo SMTP

S: 220 mx1.example.com ESMTP ready
C: HELO client.example.com
S: 250 mx1.example.com
C: MAIL FROM: <sender@example.com>
S: 250 Sender Ok
C: RCPT TO: <recipient@example.com>
S: 250 Recipient Ok
C: DATA
S: 354 End data with <CRLF>.<CRLF>
C: Subject: Test message
C:
C: This is a test message.
C: .
S: 250 Message received
C: QUIT
S: 221 closing connection

MIME

SMTP nació para texto ASCII. MIME (Multipurpose Internet Mail Extensions) lo extiende para permitir:

  • Texto en codificaciones distintas de ASCII (tildes, ñ).
  • Adjuntar objetos que no son texto (imágenes, video, PDF).
  • Mensajes con varias partes.
  • Encabezados que no están en ASCII.

Cada contenido lleva un tipo MIME, ej. application/pdf, image/png. La Web también usa estos tipos (Content-Type).

6. Escalabilidad: Balanceo de Cargas y P2P

Balanceo de Cargas

Si un servidor no da abasto, se puede usar programación multi-thread en procesadores multi-core, o usar varios servidores. ¿Cómo repartir la carga entre ellos?

  • Rotación DNS (Round Robin): el DNS entrega una IP distinta en cada resolución del nombre.
    + Muy fácil de implementar. − Reparto estático: no sabe cuántos clientes terminan en la misma IP ni la carga real.
  • HTTP Redirect: un primer servidor conoce la carga de los demás y responde con una redirección (ej. 302) al menos cargado.
    + Mejor reparto, según la carga real. − El primer servidor recibe todas las conexiones.
  • Ambas dependen de la aplicación (Web).
  • HAProxy: un proxy de balanceo para aplicaciones TCP y HTTP (capas 4 y 7) que se pone delante y reparte muy rápido las peticiones entre servidores internos. Soporta HTTPS y compresión de datos. Lo usan Twitter, GitHub, Alibaba, etc.

Modelo Peer-to-Peer (P2P)

No hay roles predefinidos: un nodo puede ser cliente y servidor a la vez. No hay administración central; los nodos se auto-organizan y el sistema se auto-mantiene.

✓ Ventajas:

Mejor balanceo de carga (más nodos tienen copias), mejor tolerancia a fallas, nodos repartidos por todo Internet.

✗ Desventajas:

Control y seguridad mucho más difíciles (ej. malware). Difícil garantizar la calidad e integridad de los datos.

  • Redes no estructuradas: los nodos se conectan sin una topología fija. Ej: Gnutella (búsqueda por inundación entre vecinos) y BitTorrent (un tracker indica qué peers tienen el archivo; clientes Transmission, qBittorrent).
  • Redes estructuradas (DHT, Distributed Hash Tables): cada dato se ubica en un nodo determinado por el hash de su clave, por lo que se encuentra en pocos saltos. Ej: Chord, Pastry, Tapestry.

Parte 2: Preguntas de Análisis Conceptual

Estas preguntas no se responden copiando la teoría: hay que aplicarla. Intenta responder antes de abrir cada una.

1. Un servidor web atiende 1.000 navegadores al mismo tiempo, todos conectados a su puerto 80. Si el puerto identifica al programa, ¿cómo sabe el SO a qué conexión pertenece cada segmento que llega?

Porque una conexión TCP no se identifica solo por el puerto del servidor, sino por la tupla completa [IP origen, puerto origen, IP destino, puerto destino, protocolo]. Los 1.000 clientes comparten IP y puerto de destino (servidor:80), pero cada uno tiene una IP distinta o, si comparten IP (ej. detrás de un NAT), un puerto efímero distinto (49152–65535). El SO crea un socket por cada conexión y usa la tupla para entregar cada segmento al socket correcto.

Esto muestra la diferencia entre puerto (un número que identifica un servicio) y socket (la interfaz de software, una por conexión).

2. Un alumno usa Telnet para administrar un servidor desde el WiFi de la biblioteca y argumenta: "igual pongo contraseña, así que es seguro". ¿Qué le responderías? ¿Qué cambia si usa SSH?

La contraseña no protege la comunicación, solo el acceso. Telnet envía todo en texto plano, contraseña incluida, así que cualquiera en la misma red puede capturarla con un sniffer o hacer un ataque Man in the Middle.

Con SSH primero se hace un handshake con criptografía asimétrica (RSA/DSA) para identificar al servidor y al usuario y acordar una clave; luego todo el tráfico va cifrado con un algoritmo simétrico (AES, 3DES), mucho más rápido. Quien capture los paquetes solo verá datos ilegibles.

3. Si HTTPS usa criptografía asimétrica, ¿por qué no cifra todos los datos de la página con ella? ¿Para qué se usa entonces?

Porque la criptografía asimétrica es muy lenta comparada con la simétrica. Se usa solo al inicio: para verificar la identidad del servidor (su certificado X509 firmado por una CA) y para intercambiar de forma segura una clave de sesión. Desde ahí, los datos van cifrados con un algoritmo simétrico usando esa clave. Es exactamente el mismo esquema que usa SSH.

4. Envías un correo a alguien@gmail.com y el servidor MX de prioridad 5 de Gmail está caído. Describe paso a paso qué hace tu MTA. ¿Cuándo recibirías un mensaje de Mailer-Daemon?
  1. El MTA consulta el DNS por los registros MX de gmail.com y los ordena por prioridad (menor valor primero).
  2. Intenta con el de prioridad 5: falla.
  3. Intenta con el siguiente (10, luego 20, ...). Lo normal es que alguno responda y el mail se entregue sin que notes nada.
  4. Si ninguno responde, deja el mail en su cola local y reintenta cada Δt.
  5. Solo si después de N intentos sigue sin poder entregarlo, abandona y te envía un error From: Mailer-Daemon.

Los múltiples MX con prioridades existen para dar tolerancia a fallas.

5. SMTP fue diseñado para texto ASCII de 7 bits. Entonces, ¿cómo es posible enviar un PDF adjunto o escribir "Ñuñoa" en el asunto?

Gracias a MIME (Multipurpose Internet Mail Extensions), una extensión que permite texto en codificaciones distintas de ASCII, adjuntar objetos que no son texto, mensajes con varias partes y encabezados no ASCII. El contenido binario se codifica (ej. Base64) para que viaje como texto, y cada parte lleva un tipo como application/pdf, que le dice al receptor cómo interpretarla.

6. ¿Es buena idea usar UDP para una aplicación de mensajería tipo WhatsApp?

Para los mensajes de texto y fotos, generalmente no. UDP no garantiza la entrega ni el orden, así que un mensaje podría perderse sin que la aplicación se entere. Se prefiere TCP (o un protocolo que agregue fiabilidad sobre UDP).

Excepción: en las llamadas de voz o video sí conviene UDP: importa más la latencia que recuperar un fragmento de audio que ya pasó.

7. Una empresa usa Rotación DNS con 3 servidores. Casi todos sus clientes están detrás del mismo proveedor de Internet, cuyo resolvedor DNS guarda en caché la respuesta. ¿Qué problema aparece?

El reparto se vuelve muy desbalanceado. La rotación DNS es estática: entrega una IP distinta por cada resolución, pero no sabe cuántos clientes van a usar cada respuesta. Si el resolvedor del ISP cachea una IP, miles de clientes terminan en el mismo servidor mientras los otros dos quedan casi libres. Además, si un servidor se cae, el DNS lo sigue entregando.

Un balanceador como HAProxy, que ve cada conexión y la carga real de los servidores, no tiene este problema.

8. En una red P2P, ¿por qué mejora el servicio cuando aumentan los usuarios, al revés que en un servidor central? ¿Qué precio se paga por eso?

Porque cada nodo es a la vez cliente y servidor: cada usuario nuevo que descarga también aporta copias y capacidad de subida, y la carga se reparte entre más nodos. En un modelo cliente-servidor, cada usuario nuevo solo agrega carga al servidor.

El precio: sin administración central, el control y la seguridad son mucho más difíciles (malware, nodos maliciosos) y cuesta garantizar la calidad e integridad de los datos y su disponibilidad.

Caso Práctico 1: Elección de Socket

Diseño de una Aplicación de Telemetría

Estás diseñando el software para un dron autónomo. El dron envía sensores de su inclinación y temperatura cada 10 milisegundos hacia un servidor en tierra para dibujarlos en una gráfica en vivo. Además, ocasionalmente el servidor en tierra le envía al dron comandos críticos como "Aterrizaje de Emergencia".

Pregunta: ¿Qué tipo de protocolo de transporte (TCP o UDP) usarías para enviar la telemetría, y cuál usarías para los comandos críticos? Justifica tu respuesta.

Resolución del Caso

1. Para la Telemetría (Sensor de datos): Usar UDP.

Justificación: El dron manda datos 100 veces por segundo. Si se pierde un paquete con la temperatura de un milisegundo específico, no sirve de nada que el protocolo lo retransmita medio segundo después, porque ya tendríamos lecturas más nuevas y actualizadas. UDP es veloz, ligero y perfecto para flujos de datos en tiempo real donde la pérdida ocasional es tolerable.

2. Para los Comandos Críticos ("Aterrizaje"): Usar TCP.

Justificación: Si el servidor manda una orden de aterrizar y el paquete se pierde, el dron se estrellaría. Para este canal se necesita TCP (Transmission Control Protocol), ya que garantiza que el mensaje llegará correctamente y en orden. Si TCP detecta que el segmento se perdió, lo retransmite automáticamente.

En código: la telemetría usaría un socket SOCK_DGRAM (sin conexión) y los comandos un socket SOCK_STREAM (con conexión). Son dos sockets distintos, en puertos distintos.

Caso Práctico 2: Balanceo de Carga

La caída del Servidor de Matrículas

La universidad ha implementado un sistema donde un servidor web principal tiene implementado un mecanismo de HTTP Redirect. Cuando un alumno entra, este servidor le responde enviando un código HTTP 302 que dice: "Ve al servidor B (IP: 200.x.x.x)".

Pregunta: El día de toma de ramos, entran 10.000 alumnos al mismo tiempo. Los servidores de apoyo B y C tienen capacidad de sobra, pero el sistema completo se cae. Basado en la arquitectura, ¿qué cuello de botella falló y cómo se solucionaría?

Resolución del Caso

El cuello de botella fue el propio servidor principal de redirección.

Análisis: El balanceo por HTTP Redirect tiene una gran debilidad: para que un cliente sea redirigido a un servidor desocupado, primero tiene que abrir una conexión TCP completa con el servidor principal, el cual debe procesar la solicitud a nivel de aplicación web y emitir una respuesta. Si 10.000 alumnos llegan de golpe, el servidor principal agota todos sus sockets disponibles y sus recursos de CPU solo tratando de redirigir, colapsando y dejando a los servidores B y C inalcanzables.

Soluciones posibles:

  • HAProxy: un proxy especializado en balanceo TCP/HTTP (capas 4 y 7), mucho más liviano que un servidor web completo, que reparte cada conexión entre B y C según su carga. Ojo: también es un punto único de falla, así que en producción se instalan dos en modo redundante.
  • Rotación DNS: reparte a los alumnos entre las IPs de B y C ya al resolver el nombre, así que ningún servidor recibe a todos. Es muy simple, pero el reparto es estático: no conoce la carga real y, si un servidor se cae, el DNS lo sigue entregando.
Caso Práctico 3: P2P y BitTorrent

Roles en una Red Descentralizada

En una arquitectura P2P usando BitTorrent, un usuario desea descargar el último sistema operativo Linux (archivo .torrent). Analizando las diapositivas de la asignatura:

Pregunta: ¿Qué rol cumple el "Tracker" dentro de la red BitTorrent? ¿El tracker almacena el archivo Linux que el usuario quiere descargar?

Resolución del Caso

1. ¿El tracker almacena el archivo?
NO. El Tracker nunca almacena el archivo (el sistema Linux). La característica central del P2P es que el archivo lo tienen los propios usuarios (Nodos/Peers).

2. ¿Qué rol cumple entonces?
El Tracker actúa como un "director de tráfico" o una libreta de direcciones. Cuando abres el archivo .torrent, tu cliente contacta al Tracker. El Tracker le responde diciendo: "No tengo el archivo, pero aquí tienes una lista de 500 IPs de otros usuarios en el mundo que sí lo están compartiendo en este instante". Tras obtener esa lista, tu computador se conecta directamente a esos usuarios (P2P) para empezar a intercambiar los trozos de archivo.

Para pensar: si el tracker se cae, los peers que ya están conectados siguen intercambiando trozos, pero los nuevos no encuentran a nadie. Por eso los clientes modernos también usan una DHT (red estructurada) para encontrar peers sin tracker.

Caso Práctico 4: Protocolos "a mano"

Hablando SMTP con Telnet

Un administrador se conecta al servidor de correo de su empresa con telnet mx1.empresa.cl 25 y escribe la siguiente sesión:

220 mx1.empresa.cl ESMTP ready
HELO pc-admin.empresa.cl
250 mx1.empresa.cl
MAIL FROM: <rector@usm.cl>
250 Sender Ok
RCPT TO: <alumno@empresa.cl>
250 Recipient Ok
DATA
354 End data with <CRLF>.<CRLF>
Subject: Suspensión de clases
...

Preguntas: (a) ¿Qué demuestra que esto funcione con Telnet sobre el tipo de protocolo que es SMTP? (b) ¿Qué problema de seguridad revela el comando MAIL FROM? (c) ¿Por qué hacer esto desde un WiFi público sería doblemente riesgoso?

Resolución del Caso

(a) SMTP es un protocolo de texto sobre TCP: comandos legibles (HELO, MAIL FROM, RCPT TO, DATA, QUIT) y respuestas con códigos numéricos (220, 250, 354, 221). Telnet solo abre una conexión TCP a un puerto y envía lo que tipeas, así que sirve para hablar con cualquier protocolo de texto. Lo mismo se puede hacer con HTTP: telnet servidor 80 y luego GET /index.html.

(b) SMTP básico no verifica el remitente: MAIL FROM acepta lo que el cliente escriba. Así se falsifican correos (spoofing). Por eso hoy los servidores exigen autenticación y usan mecanismos como SPF, DKIM y DMARC.

(c) Primero, Telnet y SMTP en el puerto 25 viajan en texto plano: todo el contenido del correo, y cualquier credencial que se envíe, se puede capturar con un sniffer. Segundo, alguien en la misma red podría hacer Man in the Middle y modificar el mensaje. La alternativa es SMTP sobre SSL/TLS (puerto 465).
