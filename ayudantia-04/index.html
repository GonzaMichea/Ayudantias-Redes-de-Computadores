Parte 1 — Análisis a Fondo de la Capa

1 Multiplexación y el Canal Abstracto

La capa de transporte provee servicios a la capa de aplicación estableciendo un canal abstracto. Su tarea fundamental es la Multiplexación y Demultiplexación (MUX/DEMUX). Las aplicaciones transmiten datos al sistema mediante Sockets; la capa de transporte mezcla (MUX) los datos de distintas apps para enviarlos por la red IP y, al llegar al destino, los separa (DEMUX) entregándolos al socket correcto según el número de puerto.

🌐

Dirección IP

Identifica la máquina destino dentro de la red.

🔌

Puerto (16 bits)

Identifica la aplicación o proceso específico en esa máquina.

🧩

Socket

Interfaz de software [IP + Puerto + Protocolo] usada por la aplicación.

2 UDP y el Formato del Datagrama

UDP (User Datagram Protocol) es sin conexión, rápido y liviano. Sin gestión de errores ni reordenamiento, acepta pérdidas. Su cabecera mide exactamente 8 Bytes (64 bits).

Puerto Fuente
Número de puerto del proceso que envía (0–65535). Permite al receptor responder al remitente correcto. Es opcional en UDP (puede ser 0 si no se necesita respuesta).

Puerto de la aplicación receptora. El SO lo usa para DEMUX y entregar el datagrama al socket correcto (ej. 53 = DNS, 67 = DHCP).

Checksum
Suma en complemento a 1 de bloques de 16 bits + pseudo-header IP (IP src, IP dst, protocolo, largo). Resultado ≠ 0xFFFF → error de transmisión. Opcional en IPv4, obligatorio en IPv6.
DATOS DE APLICACIÓN (variable)

¿Cuándo usar UDP?

  • ▸ Streaming de audio/video (pérdidas tolerables)
  • ▸ Juegos online en tiempo real (latencia crítica)
  • ▸ DNS, DHCP (mensajes pequeños y rápidos)
  • ▸ Cuando la app implementa su propio control de errores

Cálculo del Checksum

UDP suma todos los bloques de 16 bits del mensaje más un Pseudo-Header IP (IP Fuente, IP Destino, Protocolo, Largo).

La suma se calcula en 32 bits y luego se aplica el complemento a 1. Resultado ≠ 0 en el receptor → error de transmisión.

3 TCP y el Formato del Segmento

TCP (Transmission Control Protocol) es orientado a conexión y confiable. Gestiona ordenamiento, retransmisión de errores y flujo continuo de bytes mediante buffers de emisión y recepción.

Cálculo Dinámico del Time Out (RTO)

Si el RTO es muy corto genera retransmisiones innecesarias; si es muy largo reacciona lento. TCP usa un promedio exponencial ponderado (EWMA):

RTT_estimado = α × RTT_medido + (1 − α) × RTT_anterior
RTO = RTT_estimado + 4 × Desviación_RTT

Algoritmo de Karn: Ante una retransmisión, TCP duplica el RTO (Exponential Backoff) para no saturar la red. Las muestras de RTT de paquetes retransmitidos son descartadas y no contaminan el estimado.

C Los 4 Timers Claves de TCP

⏱

1. Retransmission Time Out (RTO)

Calculado dinámicamente según el RTT. Determina cuánto espera el emisor por un ACK antes de asumir pérdida y retransmitir.

🔄

2. Persistence Timer

Evita el "deadlock" cuando Window=0. Envía periódicamente 1 byte de prueba por si se perdió un ACK de actualización de ventana.

💓

3. Keep-Alive Timer

Verifica si el otro extremo sigue activo tras un largo periodo de inactividad, enviando paquetes de prueba preventivos.

⏳

4. Time-Wait / Closing (2MSL)

Al terminar la conexión, el iniciador del cierre espera 2×MSL (doble del tiempo de vida máximo) por si el último ACK se pierde y llega un FIN duplicado tardío.

Parte 3 — Preguntas Tipo Certamen

Preguntas clásicas de evaluaciones pasadas. Haz clic para revelar la justificación completa.

Un protocolo con conexión (TCP) establece un canal lógico previo mediante un Handshake de 3 pasos y mantiene memoria del estado (secuencias, ventanas, buffers). Un protocolo sin conexión (UDP) envía datagramas de inmediato sin verificar si el receptor está listo, sin garantizar entrega ni orden.
Porque se basa en una simple suma en complemento a 1 de palabras de 16 bits. Si ocurren múltiples errores que se compensan matemáticamente, o si bloques de 16 bits se permutan entre sí, la suma final dará el mismo resultado y el error no será detectado.
TCP mantiene un autómata de estados (LISTEN, ESTABLISHED, FIN_WAIT, etc.). Además almacena los números de secuencia y ACKs actuales, y mantiene buffers para datos enviados no confirmados y recibidos no procesados. Toda esta información de estado constituye su "memoria" de la conexión, a diferencia de UDP que es completamente stateless.
Window Size es la clave del Control de Flujo. Indica la memoria libre en bytes en el buffer del receptor. El emisor limita su envío a esa cantidad de bytes no confirmados. Si llega Window = 0, el emisor se bloquea y se activa el Persistence Timer hasta que el receptor libere espacio, evitando su saturación.
SCTP (Stream Control Transmission Protocol): confiable y orientado a conexión como TCP, pero basado en mensajes y con multi-homing. DCCP (Datagram Congestion Control Protocol): sin confiabilidad como UDP, pero con control de congestión avanzado similar a TCP. Útil para multimedia en tiempo real.

Parte 4 — Ejercitación Práctica y Casos

🧪 Caso Práctico: Diseño de Protocolo

Diseño de un Chat usando UDP

Pedro y Jorge están programando una aplicación de chat de texto. Para lograr la máxima velocidad y reducir el overhead de la red, deciden utilizar UDP como protocolo.

Pregunta A: ¿Es UDP una buena elección para una app de chat de texto? Justifica.

Pregunta B: ¿Qué servicios ofrece UDP y cuáles NO ofrece que serían necesarios para un chat?

Pregunta C: Si por obligación del profesor deben usar UDP, ¿qué tendrían que programar manualmente?

Resolución del Caso

Respuesta A: No es la mejor elección.

Un chat de texto requiere confiabilidad absoluta y orden de entrega. UDP no garantiza ninguna de estas propiedades: los mensajes pueden llegar desordenados ("¿Cómo hola?" antes que "hola"), perderse silenciosamente, o duplicarse. TCP es la elección natural para este caso de uso.

Respuesta B: Servicios de UDP vs. lo que necesita un chat.

✅ UDP SÍ ofrece:

  • ▸ MUX / DEMUX mediante puertos
  • ▸ Detección básica de errores (Checksum)
  • ▸ Baja latencia, sin overhead de conexión

❌ UDP NO ofrece (y el chat necesita):

  • ▸ Entrega garantizada (confiabilidad)
  • ▸ Orden de entrega de mensajes
  • ▸ Control de flujo (no saturar al receptor)
  • ▸ Control de congestión (no saturar la red)

Respuesta C: Replicar TCP en la Capa de Aplicación.

Tendrían que programar a mano todo lo que TCP hace: agregar números de secuencia a cada mensaje, implementar un sistema de ACKs propios con timers (RTO) para retransmitir mensajes perdidos, y gestionar buffers para no saturar al receptor. Es decir, estarían reimplementando TCP sobre UDP en la capa de aplicación.
