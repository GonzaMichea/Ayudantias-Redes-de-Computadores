La idea en 2 minutos

Antes de entrar en los detalles, conviene tener claro para qué existe esta capa y cuál es la diferencia de fondo entre TCP y UDP. Todo lo demás se cuelga de esto.

¿Dónde está la capa de transporte?

Aplicación tu programa (navegador, chat…)

Internet (IP) lleva paquetes entre máquinas
Enlace de datos transmisión de bits por el enlace
Física tarjeta de red, cable, radio

Le presta servicios a la capa de aplicación y usa los servicios de la capa Internet (el ruteo IP).

Analogía: un edificio de departamentos

  • Dirección IP = la dirección del edificio (identifica la máquina).
  • Puerto = el número de departamento (identifica el proceso).
  • Socket = el buzón del departamento: por ahí la aplicación entrega y recibe datos.
  • UDP = mandar una postal: rápida y barata, pero sin seguimiento. Puede perderse o llegar desordenada.
  • TCP = envío certificado con acuse de recibo: se numera todo, se confirma cada entrega y se reenvía lo perdido.

Fundamentos: canal abstracto y puertos

IP sabe llevar un paquete hasta una máquina, pero en esa máquina corren muchos programas a la vez. La capa de transporte resuelve “¿a qué programa le entrego esto?” y, según el protocolo, agrega garantías (orden, confiabilidad, flujo).

Objetivos de la capa de transporte

  • Establecer un canal abstracto entre dos procesos (no entre dos máquinas).
  • Ese canal puede ofrecer —o no— propiedades: ordenamiento, detección/corrección de errores (retransmisión), gestión de flujo y de colas.
  • UDP es el canal sin propiedades; TCP es el canal con propiedades.

Dirección IP

Identifica la máquina en la red.

Puerto (16 bits)

Identifica el proceso dentro de esa máquina. 2¹⁶ = 65 536 valores (0–65 535).

Socket

La “puerta” de software que usa la aplicación: IP + puerto + protocolo.

Multiplexación y demultiplexación

En el emisor (MUX):

  1. Varias aplicaciones escriben datos en sus sockets.
  2. Transporte le pone a cada trozo una cabecera con puerto origen y destino.
  3. Todo se “mezcla” y baja a IP por la misma interfaz de red.

En el receptor (DEMUX):

  1. IP entrega el segmento a transporte.
  2. Transporte lee el puerto destino.
  3. Entrega los datos al socket correcto (ej.: puerto 80 → servidor web).

Rangos de puertos

RangoTipoQuién lo usa
0 – 1023Bien conocidosServidores: 22 SSH, 25 SMTP, 53 DNS, 80 HTTP, 443 HTTPS
1024 – 49151RegistradosServicios registrados (ej. 3306 MySQL)
49152 – 65535DinámicosClientes (los asigna el SO)
  • El servidor escucha en un puerto bien conocido o registrado. No puede usar uno ya registrado para otro servicio.
  • El cliente siempre usa un puerto del rango dinámico (ej.: navegador en 55001 → servidor en 80).
  • Al terminar una conexión TCP, los puertos quedan libres otra vez.
Ojo con este detalle

En TCP una conexión queda identificada por 4 valores: (IP origen, puerto origen, IP destino, puerto destino). Por eso un servidor web atiende a miles de clientes “en el puerto 80” sin confundirlos: cada cliente tiene IP o puerto origen distinto. La diapositiva dice que el servidor pasa a “un puerto dinámico” al aceptar la conexión; en los sistemas actuales (sockets BSD), el socket aceptado conserva el puerto 80 y se distingue por esa 4-tupla. Para el certamen, lo importante es la idea: cada conexión tiene su propio canal.

En una frase

IP lleva datos de máquina a máquina; transporte los lleva de proceso a proceso usando puertos.

UDP — el protocolo mínimo

UDP agrega lo mínimo sobre IP: puertos (para el DEMUX) y un checksum (para detectar errores). No hay conexión, ni orden, ni retransmisión: si algo se pierde, se perdió.

Formato del datagrama cabecera = 8 bytes = 64 bits

Toca cada campo para ver qué hace.

¿Qué es el pseudo-header IP?

Para calcular el checksum, UDP “toma prestados” algunos campos de la cabecera IP y los pone imaginariamente delante del datagrama. No se transmiten; solo entran en la suma. Así el receptor también detecta si el datagrama llegó a la máquina o al protocolo equivocado.

Cálculo del checksum paso a paso

Emisor

  1. Pon el campo checksum en 0 y corta todo (pseudo-header + cabecera + datos) en palabras de 16 bits.
  2. Súmalas en un acumulador de 32 bits.
  3. Separa el resultado en dos mitades: W1 (16 bits altos) y W2 (16 bits bajos).
  4. Si W1 ≠ 0, suma el acarreo: W2 = W2 + W1.
  5. Invierte todos los bits: checksum = NOT(W2).

Receptor

  1. Mismo algoritmo, pero el acumulador parte con el checksum recibido.
  2. Suma todas las palabras, dobla el acarreo y aplica NOT.
  3. Si el resultado es 0 → correcto. Si no → error de transmisión (se descarta).

¿Por qué funciona? Sumar un número con su complemento a 1 da FFFF, y NOT(FFFF) = 0000.

Ejemplo resuelto

Supón que al cortar en palabras de 16 bits obtienes: 8A3C, 9F12, 0F0F.

// 1) suma en 32 bits 8A3C + 9F12 = 1294E 1294E + 0F0F = 0001 385D // 2) W1 = 0001, W2 = 385D → hay acarreo W2 = 385D + 0001 = 385E // 3) complemento a 1 checksum = NOT(385E) = C7A1 // Verificación en el receptor: parte con C7A1 C7A1 + 1385D = 1FFFE → FFFE + 0001 = FFFF → NOT(FFFF) = 0000 (correcto)

¿Por qué elegir UDP?

  • Más liviano: menos procesamiento y sin establecer conexión.
  • Menos ancho de banda: cabecera de 8 B (vs 20 B mínimo en TCP).
  • La aplicación no necesita retransmisiones (un dato viejo ya no sirve).
  • La aplicación quiere implementar su propio control de errores y flujo.

Aplicaciones típicas

Clásicas: DNS, NFS, SNMP, NTP — mensajes cortos tipo pregunta/respuesta.

Multimedia: streaming de audio/video, VoIP (SIP), videoconferencia — prefieren perder un trozo antes que esperar su retransmisión.

En una frase

UDP = puertos + checksum + nada más. Rápido, pero la aplicación asume el riesgo.

3

TCP — el protocolo confiable

TCP construye un canal confiable encima de IP, que no lo es. Para eso numera cada byte, confirma lo recibido, retransmite lo perdido y regula la velocidad.

Propiedades de TCP

Confiable

Todo llega, sin errores y en orden (ACK + retransmisión).

Con conexión

Handshake de 3 pasos antes de enviar datos.

↔Punto a punto y bidireccional

Un emisor y un receptor (cliente/servidor); datos en ambos sentidos a la vez.

Flujo continuo de bytes

La app escribe lo que quiera; TCP lo corta en segmentos (máximo MSS).

Pipeline con buffers

Buffers de emisión y recepción; puede haber varios segmentos “en vuelo”.

Ventana deslizante

Mecanismo para el control de flujo (no saturar al receptor).

Formato del segmento cabecera mínima 20 B · máxima 60 B

4

Números de secuencia, ACK y handshake

Esta es la parte que más se pregunta con números. Si dominas estas 4 reglas, puedes completar cualquier diagrama de certamen.

Las 4 reglas de oro

1. Seq cuenta bytes, no segmentos

Seq = número del primer byte de datos que lleva el segmento.

2. El siguiente Seq

Seq siguiente = Seq + bytes de datos
(+1 extra si el segmento lleva SYN o FIN).

3. ACK = lo que espero

Ack = próximo byte esperado = último byte recibido en orden + 1.

4. ACK acumulativo

Ack = N confirma todo hasta N−1. Un ACK puede confirmar varios segmentos.

Numeración de cada byte

El tercer segmento lleva los bytes 4400 a 4599, así que el receptor espera el 4600.

Apertura: 3-way handshake

SYN consume 1: por eso el Ack del servidor es 3001, no 3000.

El handshake, explicado

  1. Cliente → Servidor: SYN (Seq = 3000, sin datos). Informa su número de secuencia inicial (ISN). El servidor estaba en LISTEN.
  2. Servidor → Cliente: SYN + ACK (Seq = 7000, Ack = 3001). Confirma el SYN (+1), informa su propio ISN y reserva el buffer de recepción.
  3. Cliente → Servidor: ACK (Seq = 3001, Ack = 7001). Confirma el SYN del servidor. Este segmento ya puede llevar datos (aquí 200 B).

Al abrir se inicializan: los números de secuencia, los buffers y el control de flujo (tamaño de ventana). El cliente abre activamente; el servidor espera (LISTEN).

¿Por qué 3 pasos y no 2?

Cada lado tiene su propio número de secuencia, y cada uno debe ser confirmado. Con 2 pasos el servidor nunca sabría si el cliente recibió su ISN. Además, el ISN se elige al azar para que segmentos viejos de una conexión anterior no se confundan con los de la nueva.

Piggybacking

Mandar un segmento solo para un ACK desperdicia ancho de banda: el ACK viaja “a caballito” dentro de un segmento con datos.

ACK diferido

El receptor espera un poco y confirma dos segmentos con un solo ACK (es acumulativo). Ahorra ancho de banda.

5

Cierre de la conexión y autómata TCP

Como la conexión es bidireccional, cada sentido se cierra por separado: por eso el cierre ordenado tiene 4 pasos (FIN, ACK, FIN, ACK).

Terminación concertada (4 pasos)

A ya terminó, pero B todavía puede enviar datos (“medio cierre”). Ack final = 12200 + 500 + 1 (FIN) = 12701.

Paso a paso

  1. A envía FIN (puede ir con datos). El FIN consume 1 número de secuencia: 4200 + 100 + 1 = 4301. A pasa a FIN_WAIT_1.
  2. B confirma (Ack = 4301) y pasa a CLOSE_WAIT. A pasa a FIN_WAIT_2. B termina de enviar lo que le falta.
  3. B envía su FIN y pasa a LAST_ACK.
  4. A confirma (Ack = 12701), espera en TIME_WAIT y luego cierra. B recibe el ACK y cierra.
¿Para qué sirve TIME_WAIT (2·MSL)?

Si el último ACK se pierde, B reenviará su FIN; A debe seguir “vivo” para volver a confirmarlo. Además deja morir los segmentos viejos de esta conexión (MSL = vida máxima de un segmento en la red).

Terminación unilateral (RST)

RST corta la conexión de inmediato, sin handshake: se descartan los buffers y los datos pendientes.

Caso 1: conexión a un puerto cerrado

Caso 2: aborto en plena transferencia

En el caso 1 la diapositiva muestra Ack = 4000; según el RFC 793 el RST confirma el SYN, que consume 1, por lo que el valor estándar es 4001.

El autómata de estados (la “memoria” de TCP)

TCP es un autómata finito: en cada momento la conexión está en un estado, y los segmentos recibidos (o las llamadas de la app) la hacen cambiar. Los dos caminos normales son:

6

Retransmisión: cómo TCP recupera lo perdido

TCP detecta una pérdida de dos maneras: (a) pasa demasiado tiempo sin ACK (time out), o (b) llega un ACK repetido (el receptor sigue pidiendo el mismo byte).

(a) Se pierde el ACK → Time Out

A no sabe si se perdió el dato o el ACK: cuando vence el RTO, retransmite. B detecta el duplicado (ya tiene esos bytes), lo descarta y vuelve a confirmar.

(b) Se pierde un segmento → ACK duplicado

B recibe 4400 fuera de orden y vuelve a pedir 4200. A ve el ACK repetido (NOK) y retransmite 4200. Como B guardó 4400, el ACK salta a 4600.

Dato extra

En TCP real (Fast Retransmit, RFC 5681) se retransmite al recibir 3 ACK duplicados, para no reaccionar ante un simple desorden. La diapositiva lo ilustra con uno solo para simplificar.

¿Cuánto esperar antes de retransmitir? RTT y RTO

El RTT (Round Trip Time) es el tiempo que tarda un segmento en ir y su ACK en volver. El RTO (time out) debe ser algo mayor que el RTT:

RTO muy chico → retransmisiones innecesarias (el ACK venía en camino).

RTO muy grande → reacción lenta ante pérdidas reales.

Como el RTT cambia todo el tiempo, se estima dinámicamente con un promedio móvil exponencial (EWMA):

// medición RTT_medido = t_recepción_ACK − t_envío_segmento // RTT suavizado (α = 1/8) RTT = α · RTT_medido + (1 − α) · RTT_anterior // desviación promedio (β = 1/4) D = β · |RTT_medido − RTT_anterior| + (1 − β) · D_anterior // time out (δ = 4; RTT inicial alto, ~3 s) RTO = RTT + 4 · D
Algoritmo de Karn

Cada vez que ocurre un time out, se duplica el RTO (exponential backoff). Además, el RTT de un segmento retransmitido no se usa para la estimación, porque no se sabe a cuál de los envíos corresponde el ACK.

Los 4 timers de TCP

1. Retransmission Time Out (RTO)

Cuánto espera el emisor un ACK antes de retransmitir. Se calcula con la fórmula de arriba.

2. Persistence Timer

Evita quedar trabados con Window = 0 si se pierde el ACK que reabría la ventana. Al expirar se envía una sonda de 1 byte. Parte en RTT, se duplica en cada intento, máximo 60 s.

3. Keep-Alive Timer

Tras mucho tiempo sin tráfico, verifica que el otro lado siga vivo.

4. Closing Timer (TIME_WAIT)

Quien inicia el cierre espera 2·MSL antes de liberar la conexión.

Control de flujo vs control de congestión

Los dos “frenan” al emisor, pero protegen cosas distintas. Esta es una de las preguntas favoritas de certamen.

Control de flujoControl de congestión
Protege a…El receptor (que no se desborde su buffer)La red (que no colapsen las colas de los routers)
Quién fija el límiteEl receptor, explícitamente (campo Window Size)El emisor, deduciéndolo (pérdidas, time outs)
VariableVentana anunciada (rwnd)Ventana de congestión (cwnd)

Cómo se combinan

El emisor puede tener sin confirmar a lo más el mínimo de ambas: LastByteSent − LastByteAcked ≤ min(rwnd, cwnd). Y el rendimiento aproximado es ventana / RTT.

Control de flujo — el receptor

El receptor tiene un buffer: TCP lo llena con lo que llega, la aplicación lo vacía al leer. El espacio libre es la ventana que anuncia en cada segmento:

Window = BufferSize − (LastByteReceived − LastByteRead) // └──── bytes que aún esperan ser leídos ────┘

Lectura del ejemplo

  1. A envía 2 KB (Seq = 0). Buffer de B: 2/4 KB → Ack = 2048, Win = 2048.
  2. La app de A escribe 3 KB, pero solo caben 2 KB: envía 2 KB (Seq = 2048). Buffer lleno → Win = 0.
  3. A queda bloqueado con 1 KB pendiente (y arranca el Persistence Timer).
  4. La app de B lee 2 KB → B anuncia Win = 2048.
  5. A envía el 1 KB que faltaba (Seq = 4096).

Control de congestión — la red

Un router tiene colas finitas: si le llega más de lo que puede despachar, descarta paquetes. Hay dos enfoques:

  • Asistido por la red: el router avisa (bit ECN) o informa el ancho de banda disponible (RSVP).
  • Extremo a extremo (lo que hace TCP): el emisor deduce la congestión observando pérdidas y time outs.

Slow Start

Parte con cwnd = 2·MSS y la duplica cada RTT (crecimiento exponencial) hasta el umbral ssthresh.

AIMD

Sobre el umbral: +1 MSS por RTT sin pérdidas; ante una pérdida, cwnd ÷ 2.

Cautela tras time out

Un time out indica congestión grave: cwnd = 1·MSS y se vuelve a Slow Start.

8

Preguntas tipo certamen

Intenta responder en voz alta (o por escrito) antes de abrir cada respuesta.

1. ¿Cuál es la diferencia entre un protocolo con conexión y uno sin conexión?

Uno con conexión (TCP) establece un canal lógico antes de enviar datos (handshake de 3 pasos) y mantiene estado durante toda la comunicación: números de secuencia, ventanas, buffers. Uno sin conexión (UDP) envía cada datagrama de inmediato, de forma independiente, sin verificar que el receptor esté listo y sin garantizar entrega ni orden.

2. ¿Por qué se dice que el checksum de UDP/TCP es débil?

Porque es una simple suma en complemento a 1 de palabras de 16 bits. Si dos errores se compensan (un bit sube en una palabra y baja en otra) o si se intercambian dos palabras de 16 bits, la suma queda igual y el error no se detecta. Además solo detecta: no corrige.

3. ¿Por qué se dice que TCP tiene “memoria”?

Porque es un autómata de estados (LISTEN, ESTABLISHED, FIN_WAIT…) y guarda información de cada conexión: números de secuencia y ACK actuales, tamaño de ventana, estimación del RTT y buffers con datos enviados sin confirmar y recibidos sin leer. UDP, en cambio, no guarda nada entre un datagrama y otro (stateless).

4. Explique el funcionamiento del campo Window Size.

Es la base del control de flujo. En cada segmento el receptor anuncia cuántos bytes libres tiene en su buffer (BufferSize − (LastByteReceived − LastByteRead)). El emisor no puede tener más bytes sin confirmar que ese valor. Si recibe Window = 0 se bloquea y activa el Persistence Timer, que envía sondas de 1 byte hasta que el receptor anuncie espacio, evitando un bloqueo eterno si se pierde el ACK que reabría la ventana.

5. ¿Por qué SYN y FIN consumen un número de secuencia si no llevan datos?

Porque deben ser confirmados de forma confiable, igual que los datos. Si no ocuparan un número, el ACK que los confirma sería idéntico a un ACK anterior y no habría forma de saber si el SYN/FIN llegó. Al consumir 1, el ACK sube en 1 y confirma inequívocamente su recepción.

6. ¿Qué diferencia hay entre control de flujo y control de congestión?

El control de flujo protege al receptor: el límite lo anuncia él mismo con Window Size. El control de congestión protege a la red: el emisor ajusta su ventana de congestión (cwnd) según las pérdidas y time outs que observa (Slow Start, AIMD). El emisor respeta el menor de los dos límites.

7. ¿Qué pasa si el RTO es muy pequeño o muy grande? ¿Cómo lo resuelve TCP?

Muy pequeño: retransmisiones innecesarias que además cargan la red. Muy grande: reacción lenta ante pérdidas reales. TCP estima el RTT dinámicamente con un promedio móvil exponencial (α = 1/8) y su desviación (β = 1/4), y fija RTO = RTT + 4·D. Ante un time out aplica Karn: duplica el RTO.

8. ¿Para qué sirve el estado TIME_WAIT?

Quien inicia el cierre espera 2·MSL después de enviar el último ACK. Si ese ACK se pierde, el otro lado reenviará su FIN y hay que poder confirmarlo de nuevo. También evita que segmentos retrasados de esta conexión se mezclen con una nueva conexión que use los mismos puertos.

9. ¿Para qué se usa un pseudo-header IP en el checksum?

Para verificar, además del contenido, que el segmento llegó a la máquina y protocolo correctos (IP origen, IP destino, protocolo y largo). Si IP entregara un datagrama a otra máquina por error, el checksum fallaría. El pseudo-header no se transmite; solo se usa en el cálculo.

10. ¿Qué es el piggybacking y qué ventaja tiene?

Es incluir el ACK dentro de un segmento que de todas formas lleva datos en sentido contrario, en vez de mandar un segmento solo para confirmar. Ahorra segmentos y ancho de banda (cada segmento vacío cuesta al menos 40 B de cabeceras TCP + IP).

11. ¿Qué otros protocolos de transporte existen además de TCP y UDP?

SCTP: confiable y con conexión como TCP, pero basado en mensajes y con múltiples streams. DCCP: no confiable como UDP, pero con manejo de conexión y control de congestión similar a TCP; pensado para multimedia en tiempo real.

E2 · Segmento perdido y ACK acumulativo Retransmisión

A envía tres segmentos seguidos: Seq = 1000 (300 B), Seq = 1300 (400 B) y Seq = 1700 (200 B). El segundo se pierde. B guarda los segmentos que llegan fuera de orden.

  1. ¿Qué Ack envía B al recibir el primero?
  2. ¿Y al recibir el tercero?
  3. ¿Qué retransmite A?
  4. ¿Qué Ack envía B tras la retransmisión?
Ver solución
  1. Ack = 1300 (recibió bytes 1000–1299).
  2. Ack = 1300 otra vez (ACK duplicado): falta el byte 1300. Guarda 1700–1899 en el buffer.
  3. Al ver el ACK duplicado (o al vencer el RTO), A retransmite Seq = 1300 (400 B).
  4. Ack = 1900: con el hueco lleno, confirma de una vez todo hasta 1899 (acumulativo). No hay que reenviar el tercer segmento.

E3 · Cálculo del RTO RTT/RTO

Con α = 1/8, β = 1/4 y δ = 4: el RTT anterior es 100 ms, la desviación anterior es 20 ms y se mide un RTT de 140 ms. Calcula el nuevo RTT, D y RTO. Si luego ocurre un time out, ¿cuál es el nuevo RTO?

Ver solución
RTT = 1/8 · 140 + 7/8 · 100 = 17,5 + 87,5 = 105 ms D = 1/4 · |140 − 100| + 3/4 · 20 = 10 + 15 = 25 ms RTO = 105 + 4 · 25 = 205 ms Time out → Karn duplica: RTO = 410 ms

E5 · Ventana de recepción Control de flujo

El buffer de recepción de B mide 8000 B. B ha recibido hasta el byte 6000 (LastByteReceived) y su aplicación ha leído hasta el 2500 (LastByteRead).

  1. ¿Qué Window anuncia B?
  2. Si A tiene 1500 B enviados sin confirmar, ¿cuánto más puede enviar?
  3. ¿Qué pasa si la app de B deja de leer?
Ver solución
  1. Bytes en el buffer = 6000 − 2500 = 3500 → Window = 8000 − 3500 = 4500 B.
  2. 4500 − 1500 = 3000 B más.
  3. El buffer se llena, B anuncia Window = 0, A se bloquea y usa el Persistence Timer para enviar sondas de 1 byte hasta que B vuelva a tener espacio.

E7 · Caso de diseño: un chat sobre UDP Integrador

Pedro y Jorge programan un chat de texto. Para lograr la máxima velocidad y reducir el overhead, deciden usar UDP.

  1. ¿Es UDP una buena elección para un chat de texto? Justifica.
  2. ¿Qué servicios ofrece UDP y cuáles no ofrece que el chat necesitaría?
  3. Si el profesor los obliga a usar UDP, ¿qué tendrían que programar ellos?
Ver solución

A. No es la mejor elección. Un chat necesita que todos los mensajes lleguen y en orden. Con UDP un mensaje puede perderse en silencio, duplicarse o llegar desordenado (“¿cómo estás?” antes que “hola”). Además, el ahorro de overhead es irrelevante para mensajes de texto tan pequeños y poco frecuentes. TCP es la elección natural.

UDP sí ofrece
  • MUX/DEMUX con puertos
  • Detección de errores (checksum)
  • Baja latencia, sin conexión
UDP no ofrece (y el chat necesita)
  • Entrega garantizada
  • Orden de los mensajes
  • Control de flujo
  • Control de congestión

C. Reimplementar lo esencial de TCP en la capa de aplicación: números de secuencia en cada mensaje, ACK propios, un timer para retransmitir lo no confirmado, detección de duplicados y un buffer para reordenar. En la práctica estarían escribiendo “un TCP casero” sobre UDP.

Resumen para el certamen

Fórmulas clave

Seq siguiente = Seq + datos (+1 si SYN/FIN) Ack = último byte en orden + 1 Cabecera TCP = Data Offset × 4 B (5 → 20 B) Cabecera UDP = 8 B Window = Buffer − (LastRcvd − LastRead) LastSent − LastAcked ≤ min(rwnd, cwnd) Rendimiento ≈ ventana / RTT RTT = 1/8·RTTmed + 7/8·RTTant D = 1/4·|RTTmed − RTTant| + 3/4·Dant RTO = RTT + 4·D (time out → ×2) checksum = NOT(suma 16 bits con acarreo) receptor OK ⇔ resultado = 0

Errores comunes

  • Creer que Seq cuenta segmentos: cuenta bytes.
  • Olvidar que SYN y FIN consumen 1 número de secuencia.
  • Poner como Ack el último byte recibido: es el siguiente que se espera.
  • Confundir flag ACK con número de ACK.
  • Mezclar control de flujo (receptor, Window) con congestión (red, cwnd).
  • Decir que el checksum corrige errores: solo los detecta.
  • Decir que UDP no tiene puertos o checksum: sí los tiene.
  • Pensar que el cierre es de 3 pasos: son 4 (cada sentido cierra por separado).
