Parte 1: Conceptos Fundamentales

1. La Capa de Aplicación y sus Protocolos

La capa de aplicación provee una forma de comunicar aplicaciones entre sí (y, por lo tanto, a los usuarios) implementando protocolos de alto nivel:

ServicioProtocolos
WebHTTP, HTTPS

¿Qué es un Protocolo de Aplicación?

En general, un protocolo es un conjunto de reglas que gobiernan el intercambio o la transmisión de datos entre dispositivos. Concretamente, un protocolo de nivel aplicación es el conjunto de reglas para que una aplicación y un servidor (o dos o más aplicaciones) puedan:

Controlar la comunicación

  • Iniciar una comunicación.
  • Intercambiar datos sin problemas de formato (sintaxis y semántica comunes).
  • Terminar una comunicación.

Definir el servicio

  • Los servicios entregados por el servidor.
  • La forma de pedir esos servicios (datos, parámetros).
  • La forma de las posibles respuestas, incluyendo los errores.

Analogía de la clase: una conversación humana también sigue un protocolo. Se abre con un saludo ("Hola" / "Hola"), se hace una petición y se recibe una respuesta ("¿Qué hora es?" / "Son las 15:47") y se cierra ("Gracias" / "Hasta luego"). Los protocolos de red formalizan exactamente esas tres fases.

2. Encapsulación y Flujo de Bits

Los protocolos actúan como muñecas rusas: el mensaje de aplicación desciende por las capas y cada una lo envuelve con su propio encabezado (header). En destino ocurre el proceso inverso (desencapsulación): cada capa quita su encabezado y entrega el resto a la capa superior.

Data Link HeaderDir. MAC (Trama)
IP HeaderDir. IP (Paquete)
Transport HeaderPuerto TCP/UDP (Segmento)
Application DataMensaje original (HTTP, SMTP, etc.)
Data Link TrailerControl de errores (CRC)

Del mensaje a los bits: la capa de enlace agrega un encabezado y también un trailer al final de la trama. Esa trama completa se transmite como un flujo de bits, que la capa física convierte en señales eléctricas, pulsos de luz o radiofrecuencias (Wi-Fi) según el medio.

3. Puertos, IANA, IETF y Port Forwarding

Un servidor puede ofrecer varios servicios a la vez. La dirección IP no basta para identificar la aplicación de destino, por eso se usa un número de puerto en el nivel del protocolo de transporte. Ejemplo: un cliente se conecta a 200.1.19.1:25 y el servidor entrega la conexión al servicio de correo (SMTP); el puerto 80 iría al servidor web y el 22 a SSH.

Rangos de puertos (IANA)

El puerto es un entero entre 0 y 65535. La IANA (Internet Assigned Numbers Authority) los asigna y clasifica así:

  • 0 - 1023  Bien conocidos (well-known): servicios del sistema operativo o de gestión de Internet (22, 25, 80, 443). En Unix/Linux, abrir uno de estos puertos requiere permisos de root.
  • 1024 - 49151  Registrados: protocolos aceptados y normalizados por el IETF.
  • 49152 - 65535  Dinámicos o efímeros: los usan las conexiones TCP para liberar el puerto principal del servidor y los clientes como puerto de origen. Al cerrarse la conexión, el puerto queda disponible de nuevo.

Tabla de servicios del SO

El sistema operativo mantiene una copia de la tabla nombre de servicio ↔ puerto. En Linux está en /etc/services:

ftp-data 20/tcp ftp 21/tcp ssh 22/tcp # SSH Remote Login Protocol telnet 23/tcp smtp 25/tcp http 80/tcp https 443/tcp

¿Cómo se asigna un puerto? El proceso RFC

Cualquier persona puede proponer un protocolo al IETF (Internet Engineering Task Force). El ciclo es:

1. IETF

Acepta y normaliza el protocolo. Publica el RFC-XXX versión 1.

2. IETF

Revisa los comentarios (Request For Comments) y hace modificaciones.

3. IANA

Asigna uno o más números de puerto.

4. IETF

Publica la versión final: RFC-XXX definitiva.

Servidores con IP privada: Port Forwarding

Si el servidor está en una red privada (ej. 10.1.1.20), no es alcanzable directamente desde Internet. Se configura Port Forwarding en el NAT del router: las peticiones que llegan a la IP pública en un puerto dado se traducen hacia la IP privada correspondiente.

Cliente ──► 200.1.19.3:25 (IP pública del router) │ NAT / Port Forwarding ▼ 10.1.1.20:25 (servidor de correo en la red privada)

4. La Interfaz Socket: UDP y TCP

La interfaz socket (UNIX/Linux y Windows) es la API que permite a un programa intercambiar datos entre cliente y servidor. Al crear un socket con socket() se elige el tipo de transporte:

  • SOCK_STREAM (TCP): canal abstracto con conexión, con control de pérdidas, de orden y de flujo.
  • SOCK_DGRAM (UDP): canal abstracto sin conexión y sin ningún control: cada mensaje viaja de forma independiente.

El Puerto

Es solo un identificador numérico (como el número de departamento en un edificio). Le dice al sistema operativo a qué programa entregar el mensaje.

El Socket

Es el punto extremo lógico de comunicación que el programa abre a través de la API del sistema operativo. Queda definido por IP + puerto + protocolo de transporte. Una conexión TCP se identifica por el par de sockets de ambos extremos.

5. Terminal Remoto: TELNET vs SSH

TELNET

Puerto 23RFC-15, RFC-854

Protocolo cliente-servidor sobre TCP para abrir una terminal virtual remota (u otro tipo de servidor). Sintaxis: telnet servidor [puerto].

  • Lo que tipea el usuario se transmite al servidor; en modo terminal (puerto 23) lo interpreta un shell (bash, ...).
  • Incluye una negociación del tipo de terminal (secuencias de escape).
  • El cliente recibe y muestra la respuesta.

El problema: todas las comunicaciones pasan en claro, sin cifrado. Una contraseña viaja como texto legible y cualquiera que capture el tráfico (sniffing) o se interponga en la comunicación (Man in the Middle) puede leerla. Conclusión de la clase: usar SSH.

SSH (Secure Shell)

Puerto 22RFC-4253

Protocolo cliente-servidor sobre TCP y cifrado. Sirve para terminal virtual y también para crear túneles cifrados. Sintaxis: ssh user@machine.subdomain.domain.

Usa dos tipos de algoritmos:

  • Asimétrico (RSA/DSA): para la identificación del usuario.
  • Simétrico (AES, 3DES, Blowfish): para el intercambio de datos, porque es mucho más rápido.

La solución: desde la autenticación hasta cada comando viaja cifrado. Quien intercepte el tráfico solo verá datos ilegibles.

SSH Handshake (Diffie-Hellman)

  1. 1Cliente y servidor se ponen de acuerdo en un número primo público y en el algoritmo de cifrado simétrico (ej. AES).
  2. 2Cada uno genera un número secreto (a y b), que es su clave privada, y a partir de él calcula su clave pública.
  3. 3Se intercambian las claves públicas por la red.
  4. 4Cada lado combina su secreto con la clave pública del otro y ambos obtienen la misma clave secreta simétrica compartida, sin que esta haya viajado nunca por la red.
  5. 5Esa clave cifra el resto de la comunicación.

SSH: Identificación del usuario por clave

  1. 1El cliente envía su ID y el número de su clave.
  2. 2El servidor busca la clave pública del cliente en sus claves autorizadas (authorized keys). Si no existe, termina.
  3. 3El servidor genera un número aleatorio, lo cifra con la clave pública del cliente y se lo envía (desafío).
  4. 4Solo el dueño de la clave privada puede descifrarlo. El cliente responde con un hash MD5 del número junto con la clave simétrica compartida.
  5. 5El servidor calcula el mismo MD5 y compara: si son iguales, el cliente queda identificado; si no, la conexión se rechaza.

6. Correo Electrónico: SMTP, MX y MIME

Puertos 25, 465 (SSL/TLS)RFC-821, RFC-5321

SMTP (Simple Mail Transfer Protocol) y su versión extendida ESMTP permiten transmitir correos entre usuarios de redes diferentes, sin saber dónde se encuentra físicamente el destinatario: basta con su dirección de correo. El email fue la primera killer application de Internet y tiene tres elementos básicos:

User Agent (UA)

El programa del usuario para leer y escribir correos: mail, elm, mutt, Thunderbird, Outlook, Webmail.

Mail Transfer Agent (MTA)

El servidor de correo: la infraestructura misma. Transfiere los mails, maneja las colas de espera y los buzones locales. Ej: sendmail, postfix.

El protocolo

SMTP / ESMTP para enviar entre MTAs. Para que el usuario lea su buzón se usan IMAP o POP3.

¿Cómo se encuentra el servidor de destino? El registro MX

Para un correo a xavier.bonnaire@gmail.com, el MTA local toma el dominio (gmail.com) y consulta al DNS por sus registros MX (Mail Exchanger). Cada MX tiene una prioridad: menor valor = mayor prioridad.

$ dig gmail.com mx ;; ANSWER SECTION: gmail.com. 309 IN MX 20 alt2.gmail-smtp-in.l.google.com. gmail.com. 309 IN MX 40 alt4.gmail-smtp-in.l.google.com. gmail.com. 309 IN MX 5 gmail-smtp-in.l.google.com. <- menor valor: se intenta primero gmail.com. 309 IN MX 10 alt1.gmail-smtp-in.l.google.com. gmail.com. 309 IN MX 30 alt3.gmail-smtp-in.l.google.com.

El DNS no entrega los registros ordenados: el orden lo decide el número de prioridad, no la posición en la respuesta.

Algoritmo de envío del MTA

  1. 1Pregunta al DNS por el MX del dominio de destino.
  2. 2Pregunta al DNS la IP del MX elegido (ej. 64.233.190.26).
  3. 3Intenta entregar al MX de mayor prioridad. Si falla, intenta con el siguiente.
  4. 4Si ninguno responde, deja el correo en su cola local.

Gestión de la cola

  • Cada intervalo Δt, el MTA recorre su cola.
  • Para cada correo, intenta enviarlo al MX de mayor prioridad (o a uno de mejor prioridad que él mismo, si el MTA es un MX de respaldo).
  • Si tras N intentos no lo logra, abandona y envía un mensaje de error al remitente (el clásico "From Mailer-Daemon...").

Una sesión SMTP real (vía telnet)

SMTP es un protocolo de texto: cada comando del cliente recibe un código numérico de respuesta del servidor (220 listo, 250 OK, 354 envía los datos, 221 cerrando).

$ telnet mx1.example.com smtp S: 220 mx1.example.com ESMTP server ready C: HELO client.example.com S: 250 mx1.example.com C: MAIL from: <sender@example.com> S: 250 Sender <sender@example.com> Ok C: RCPT to: <recipient@example.com> S: 250 Recipient <recipient@example.com> Ok C: DATA S: 354 Ok Send data ending with <CRLF>.<CRLF> C: Subject: Test message C: C: This is a test message. C: . <- una línea con solo un punto termina el mensaje S: 250 Message received C: QUIT S: 221 mx1.example.com ESMTP server closing connection

MIME (Multipurpose Internet Mail Extensions)

RFC-2045, 2046, 2047, 2049, 4288, 4289

SMTP original solo transporta texto ASCII. MIME lo extiende para permitir:

  • Texto en codificaciones distintas de ASCII (tildes, eñes, otros alfabetos).
  • Adjuntar objetos que no son texto (imágenes, video, PDF...).
  • Mensajes compuestos de varias partes.
  • Encabezados que no están en ASCII.

Cada contenido se etiqueta con un tipo MIME, por ejemplo application/pdf para .pdf o application/x-shockwave-flash para .swf. Los mismos tipos se usan en la Web (encabezado Content-Type).

7. La Web y HTTP

Puertos 80 (HTTP), 443 (HTTPS)RFC-2068, RFC-2616

La World Wide Web nace a principios de los 90 en el CERN, al principio solo con enlaces de hipertexto. Se apoya en tres piezas: HTTP (HyperText Transfer Protocol), HTTPS (HTTP seguro sobre TLS/SSL) y HTML (HyperText Markup Language). HTTP sigue el modelo cliente-servidor y es stateless (sin estado): el servidor no recuerda peticiones anteriores del mismo cliente, por eso existen las cookies (encabezado Set-Cookie).

¿Qué hace el navegador?

  1. 1Resuelve el nombre del servidor con el DNS (www.usm.cl → 200.1.30.100).
  2. 2Se conecta al servidor usando esa IP; el servidor atiende la conexión en un hilo.
  3. 3Pide la primera página: GET /index.html (o index.php...).
  4. 4Por cada enlace u objeto de la página (imágenes, CSS...) hace una nueva petición, al mismo servidor o a otro.

Páginas estáticas vs dinámicas

Estáticas: su contenido no cambia en el tiempo. El servidor lee el archivo (ServerRoot/index.html) y lo envía tal cual.

Dinámicas: su contenido no está fijo. El servidor lee index.php, lo pasa a un intérprete (PHP) que genera el HTML en ese momento, y envía ese HTML generado al navegador.

HTTP a mano: también es un protocolo de texto

Con telnet al puerto 80 se puede hablar HTTP directamente. La respuesta trae un código de estado (200 OK, 301 Moved Permanently, 302 Found, 404 Not Found...) y encabezados como Content-Type o Set-Cookie.

$ telnet www.inf.utfsm.cl 80 GET /index.html <title>301 Moved Permanently</title> <p>The document has moved <a href="https://www.inf.utfsm.cl/index.html">here</a>. Connection closed by foreign host. # El servidor redirige al cliente hacia la versión HTTPS del sitio.

8. HTTPS y Certificados X509

Al igual que TELNET, en HTTP todo pasa en claro, lo que genera problemas de confidencialidad con contraseñas y formularios con datos privados. La solución es HTTPS = HTTP sobre SSL/TLS, que cifra la comunicación. Se usa criptografía asimétrica para autenticar al servidor y acordar una clave, y luego cifrado simétrico para los datos. Para esto el servidor necesita un certificado X509 entregado por una Autoridad de Certificación.

¿Cómo se obtiene un certificado?

  1. 1La organización envía la información del servidor a la CA: nombre, dirección IP, responsable, organización, fecha de inicio y de vencimiento, y su clave pública.
  2. 2La CA genera el certificado y lo firma con su clave privada.
  3. 3La CA transmite el certificado a la organización, que lo instala en su servidor web.

Cadena de confianza

Los certificados forman una jerarquía. Ejemplo real del certificado de la USM:

GeoTrust Global CA (CA raíz) └─ RapidSSL SHA256 CA - G3 (CA intermedia) └─ *.usm.cl (servidor)

El navegador trae preinstaladas las claves públicas de las CA raíz de confianza (Verisign, Thawte, GeoTrust...) y con ellas verifica las firmas de la cadena.

Verificación y excepciones en el navegador

Al conectarse por HTTPS, el servidor envía su certificado y el navegador revisa si es válido. Si lo es, la conexión HTTPS continúa. Si no, aparece la alerta "Your connection is not secure" y el usuario puede volver atrás o agregar una excepción (que agrega esa autoridad a la lista de confianza del navegador). Causas típicas de un certificado inválido:

ProblemaSignificado
Autofirmado (SEC_ERROR_UNKNOWN_ISSUER)Lo firmó el propio servidor y no una CA de confianza.
ExpiradoLa fecha actual es posterior a la fecha de vencimiento.
Nombre incorrectoEl certificado fue emitido para otro dominio.
Firma no válidaEl certificado fue alterado o la cadena no llega a una CA de confianza.

9. Balanceo de Carga

Un servidor puede recibir más conexiones de las que puede atender. Soluciones: usar programación multi-hilo en procesadores multi-core, o usar varios servidores. En ese caso, hay que decidir cómo repartir la carga:

Rotación de DNS

El DNS tiene varias IPs para www.domain.com y entrega una distinta en cada resolución (round robin).

A favor: muy fácil de implementar.

En contra: la repartición es estática; no se sabe cuántos clientes irán a la misma IP (las respuestas quedan en caché) ni si ese servidor está cargado o caído.

HTTP Redirect

Parte del protocolo HTTP. (1) El cliente se conecta al servidor principal, (2) este responde con una redirección hacia, por ejemplo, www2.domain.com, (3) el cliente se conecta allí y hace su GET.

A favor: mejor repartición; el primer servidor mantiene el estado de carga de los otros y decide (ej. round robin).

En contra: dos conexiones por cliente y el servidor principal es un cuello de botella.

Proxy: HAProxy

Un proxy se ubica delante de los servidores y reenvía cada conexión a uno de ellos; el cliente nunca los ve directamente.

  • Balancea aplicaciones TCP y HTTP.
  • Distribución muy rápida de peticiones.
  • Soporta HTTPS y compresión de datos.
  • Usado por Twitter, GitHub, Alibaba, Bitbucket...

Idea clave de la clase: la rotación de DNS y el HTTP Redirect dependen de la aplicación (están pensados para la Web). Un proxy como HAProxy, al trabajar a nivel TCP, sirve para cualquier aplicación TCP, además de HTTP.

10. El Modelo Peer to Peer (P2P)

Características

  • No hay roles predefinidos: un nodo puede ser cliente y servidor a la vez.
  • Los datos son accesibles a través del conjunto de nodos que forman el sistema.
  • No hay administración central: los nodos se auto-organizan y el sistema se auto-mantiene.

Ventajas

  • Mejor balanceo de carga: más nodos tienen copias, y la capacidad crece con cada usuario.
  • Mejor tolerancia a fallas: los nodos están repartidos por todo Internet.

Desventajas

  • Control y seguridad mucho más difíciles (malware, contenido ilegal).
  • Calidad e integridad de los datos no garantizadas; tampoco su disponibilidad si los nodos que los tienen se desconectan.
TipoEjemploCómo se encuentra un archivo
No estructurada Gnutella (clientes tipo eMule) Los nodos se conectan sin un orden fijo y las búsquedas se propagan de vecino en vecino.
No estructurada con tracker BitTorrent (Transmission, qBittorrent) El archivo .torrent indica el nombre del contenido y la lista de trackers. Los peers se registran en el tracker, que entrega la lista de otros peers. Luego los trozos del archivo se intercambian directamente entre peers.
Estructurada (DHT) Pastry, Chord, Tapestry, Symphony Los nodos se ordenan en un anillo según una función hash (Distributed Hash Table). La búsqueda salta de nodo en nodo hacia el responsable de esa clave, y luego el documento se baja directamente desde el nodo que lo tiene.

Caso Práctico 1: Elección de Socket

Diseño de una Aplicación de Telemetría

Estás diseñando el software de un dron autónomo. El dron envía lecturas de inclinación y temperatura cada 10 milisegundos a un servidor en tierra que las dibuja en una gráfica en vivo. Ocasionalmente, el servidor le envía comandos críticos como "Aterrizaje de Emergencia".

Pregunta: ¿Qué protocolo de transporte (TCP o UDP) usarías para la telemetría y cuál para los comandos críticos? ¿Qué tipo de socket crearías en cada caso? Justifica.

Resolución del Caso

1. Telemetría: UDP (socket SOCK_DGRAM).

El dron envía 100 lecturas por segundo. Si se pierde una, no sirve retransmitirla después, porque ya llegaron lecturas más nuevas. UDP no establece conexión ni retransmite: es rápido y liviano, ideal para flujos en tiempo real donde una pérdida ocasional es tolerable.

2. Comandos críticos: TCP (socket SOCK_STREAM).

Si la orden de aterrizar se pierde, el dron podría estrellarse. TCP (Transmission Control Protocol) garantiza la entrega y el orden: si detecta que un segmento se perdió, lo retransmite automáticamente.

Caso Práctico 2: Balanceo de Carga

La caída del Servidor de Matrículas

La universidad implementó un servidor web principal con HTTP Redirect. Cuando un alumno entra, este servidor le responde con un código HTTP 302 que dice: "Ve al servidor B (IP: 200.x.x.x)".

Pregunta: El día de toma de ramos entran 10.000 alumnos al mismo tiempo. Los servidores B y C tienen capacidad de sobra, pero el sistema completo se cae. ¿Qué cuello de botella falló y cómo se solucionaría?

Resolución del Caso

El cuello de botella fue el propio servidor principal de redirección.

Análisis: con HTTP Redirect, todo cliente debe primero abrir una conexión TCP completa con el servidor principal, que procesa la petición HTTP y responde con la redirección. Recién después el cliente abre una segunda conexión con B o C. Si 10.000 alumnos llegan de golpe, el servidor principal agota sus conexiones y su CPU solo redirigiendo; al caer, B y C quedan inalcanzables aunque estén libres. Es un punto único de falla.

Solución: usar un proxy de balanceo como HAProxy, que reparte cada conexión TCP/HTTP muy rápido sin exigir una segunda conexión al cliente, o la rotación de DNS, que reparte las IPs antes de que el alumno toque los servidores (aunque de forma estática). En la práctica se combinan: varias instancias de proxy publicadas con rotación DNS.

Caso Práctico 3: P2P y BitTorrent

Roles en una Red Descentralizada

Un usuario quiere descargar la última imagen ISO de una distribución Linux usando BitTorrent, a partir de un archivo .torrent.

Pregunta: ¿Qué contiene el archivo .torrent? ¿Qué rol cumple el "Tracker"? ¿El tracker almacena el archivo que el usuario quiere descargar?

Resolución del Caso

1. El .torrent no contiene el archivo: contiene su descripción (nombre, trozos) y la lista de trackers a los que hay que contactar.

2. ¿El tracker almacena el archivo? No. En P2P el archivo lo tienen los propios usuarios (peers).

3. Rol del tracker: funciona como una libreta de direcciones. Los peers se registran en él; cuando tu cliente lo contacta, responde con una lista de IPs de otros peers que comparten ese archivo en ese momento. Con esa lista, tu computador se conecta directamente a ellos y empieza a intercambiar trozos, descargando y subiendo al mismo tiempo.

Caso Práctico 4: Correo y Registros MX

Un correo que no llega

El dominio empresa.cl tiene estos registros MX:

empresa.cl. IN MX 20 respaldo.empresa.cl. empresa.cl. IN MX 10 mail.empresa.cl.

Pregunta: Un usuario de USM envía un correo a ana@empresa.cl. (a) ¿A qué servidor intenta entregar primero el MTA de la USM? (b) ¿Qué ocurre si mail.empresa.cl está caído? (c) ¿Y si ambos servidores están caídos durante varios días?

Resolución del Caso

(a) A mail.empresa.cl, porque tiene el valor MX más bajo (10) y, por lo tanto, la mayor prioridad. El orden en que el DNS lista los registros no importa.

(b) El MTA intenta con el siguiente: respaldo.empresa.cl (20). Ese servidor de respaldo guarda el correo en su cola e intenta reenviarlo al MX de mejor prioridad que él (el 10) cuando vuelva a estar disponible.

(c) El MTA de la USM deja el correo en su cola local y reintenta cada Δt. Si tras N intentos no logra entregarlo, abandona y le envía al remitente un mensaje de error del Mailer-Daemon.

Caso Práctico 5: Certificados X509

"Your connection is not secure"

Al entrar a hiperion.spa.inf.utfsm.cl, Firefox muestra: "The certificate is not trusted because it is self-signed", "The certificate expired on 17/10/13" y el código SEC_ERROR_UNKNOWN_ISSUER.

Pregunta: Explica cada uno de los problemas. ¿Qué implica para la seguridad presionar "Add Exception"? ¿Cómo debería corregirlo el administrador?

Resolución del Caso

Autofirmado / emisor desconocido: el certificado no fue firmado por una CA de la lista de confianza del navegador sino por el propio servidor. El navegador no tiene cómo comprobar que ese servidor es quien dice ser.

Expirado: la fecha actual supera la fecha de vencimiento incluida (y firmada) en el certificado, así que ya no es válido aunque estuviera bien firmado.

Agregar una excepción: la comunicación seguirá cifrada, pero se pierde la garantía de autenticidad: si un atacante hiciera un Man in the Middle presentando su propio certificado autofirmado, el usuario no podría distinguirlo. Solo es razonable si se sabe con certeza que el servidor es el legítimo.

Corrección: el administrador debe obtener un certificado nuevo, emitido y firmado por una CA de confianza, para el nombre de dominio correcto y con una fecha de vencimiento vigente.
